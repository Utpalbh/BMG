CONFIDENTIAL / PROJECT WORKING MATERIAL
1. Executive Summary
BM&G's current examination intake is fragmented across JetDocs, LoanTrack, EDM, MS Access, ClosingExpress, and SecureDocs. The existing process requires a coordination desk to manually create a LoanTrack transaction/invoice number, manually upload documents to EDM, manually add the invoice number to the MS Access queue, and distribute work. The broader modernization proposal targets replacement of these legacy handoffs and later AI-assisted examination, but the agreed MVP is deliberately much smaller.
AGREED MVP IN ONE SENTENCE
When a lender submission arrives through JetDocs, automatically take the files from the temporary on-premises landing location, send them privately to an Azure AI service for document classification and extraction of the small metadata set required for invoice creation, create the LoanTrack invoice/transaction, and then upload the original documents to EDM using the resulting invoice number as the reference.
The MVP ends after successful EDM upload. The current MS Access queue, work distribution, ClosingExpress examination process, approximately 140 examination fields, review checklist, and SecureDocs release process remain unchanged.
Recommended PoC technology direction
On-premises orchestration: .NET 8 Worker Service running near the JetDocs temporary folder and existing LoanTrack/EDM systems.
Azure AI: Azure AI Document Intelligence v4.0 using a custom classifier and custom extraction models for MVP metadata. Azure OpenAI is not required for the first PoC unless metadata complexity justifies it.
Private connectivity: Site-to-Site IPsec/IKE VPN from BM&G on-premises to an Azure VNet; Document Intelligence reachable only through a Private Endpoint; public network access disabled.
DNS: on-premises DNS forwards Azure private-service queries to Azure DNS Private Resolver so the normal service FQDN resolves to the Private Endpoint IP.
PoC adapters: simulated Invoice and EDM implementations until the real LoanTrack/EDM contracts are confirmed.

4. End-to-End MVP Process
Figure 1 - Confirmed MVP flow and stop point. The orange box is intentionally outside the automation boundary.
Happy path
1.  
Lender uploads documents in JetDocs.
2.  
JetDocs/current integration places the documents in an on-premises temporary submission folder and/or emits a trigger.
3.  
The MVP Intake Worker receives the trigger and establishes a submission/correlation ID.
4.  
The worker waits until the submission is stable/complete enough to process, then computes file hashes and checks idempotency.
5.  
Documents are sent over HTTPS through the S2S VPN to Azure AI Document Intelligence through its Private Endpoint.
6.  
The AI service classifies each document and runs the configured extraction model for that class.
7.  
The worker normalizes extraction results into canonical InvoiceMetadata using configurable source-priority rules.
8.  
Required fields and confidence thresholds are validated.
9.  
The Invoice Adapter creates the LoanTrack transaction/invoice and returns the invoice number.
10.  
The invoice number is persisted before EDM upload starts.
11.  
The EDM Adapter uploads/associates every original document with that invoice number.
12.  
The submission is marked Completed. Existing MS Access queue and downstream examination/release continue unchanged.
Invoice creation gate
Do not create an invoice when the submission cannot be correlated, required metadata is missing, confidence is below the approved threshold, authoritative-source conflicts cannot be resolved, or the submission has already produced an invoice. These cases go to Manual Exception.
5. Functional Requirements
ID
Requirement
FR-01 Intake trigger
Begin processing when a JetDocs-related trigger indicates a new lender submission is available. PoC uses a file-system/folder watcher; production trigger mechanism remains TBD.
FR-02 Submission grouping
Process one logical submission as an atomic unit. A trigger or folder structure must provide a stable submission ID.
FR-03 Stable-file detection
Do not upload files still being copied. Use manifest/completion marker, atomic rename, or repeated size/last-write checks.
FR-04 Duplicate prevention
Persist an idempotency key using source submission ID plus document hashes. Replayed triggers must not create a second invoice.
FR-05 Classification
Classify configured document classes. Initial candidates: Note, DeedOfTrust, TitleCommitment, Survey, ClosingInstructions, Rider, Unknown.
FR-06 Metadata extraction
Extract only metadata required for MVP invoice creation. Final fields/source mappings are business TBD.
FR-07 Confidence/provenance
Retain value, source document/page when available, confidence, model ID/version.
FR-08 Canonical aggregation
Map document-level results into InvoiceMetadata using configuration-driven source precedence.
FR-09 Validation
Required fields and confidence thresholds must gate invoice creation.
FR-10 Invoice creation
Create LoanTrack transaction/invoice through an adapter; actual supported LoanTrack integration surface is TBD.
FR-11 EDM upload
After invoice creation, upload/associate original lender files to EDM using invoice number.
FR-12 Partial EDM protection
Track per-document upload state so interrupted uploads can resume without duplicate documents.
FR-13 Status/audit
Persist correlation ID, hashes, stage, attempts, AI results summary, invoice number, EDM status, timestamps/errors.
FR-14 Manual exception
Non-retryable/business validation failures must be visible and recoverable; never silently discard.
FR-15 Downstream preservation
Do not create MS Access queue entries or alter ClosingExpress/SecureDocs behavior in MVP.

9. Azure AI Document Intelligence Design
Recommended first implementation
1.  
Custom classifier identifies document type.
2.  
Custom neural extraction model per supported class returns configured fields.
3.  
On-prem aggregation resolves source precedence and canonical invoice metadata.
This keeps the first PoC focused on purpose-built document AI and avoids adding an LLM before the metadata is known. Azure OpenAI can be introduced later only if extraction requires semantic reasoning that Document Intelligence cannot reliably provide.
Training data
Microsoft documents a minimum of two classes and five samples per class for a custom classifier, and custom extraction can start with five examples of a document type. The included synthetic dataset supplies five samples for each of six candidate classes (30 PDFs).
Runtime and training storage
The on-prem worker can send document bytes directly to the Analyze API/SDK. Azure Blob Storage is included primarily for custom-model training. If storage is network-restricted, give it a Blob Private Endpoint and configure Document Intelligence managed-identity access required for training.
DATA RETENTION REVIEW REQUIRED
Microsoft states that Document Intelligence temporarily stores submitted input and analyze results in encrypted Azure Storage in the same region and retains them for up to 24 hours. The Delete Analyze Result API can remove them sooner. Because the original proposal said mortgage data would remain on premises, this revised behavior needs explicit security/legal approval.
Authentication
PoC may use an API key stored outside source control or a Microsoft Entra service principal. Production should prefer Entra service-to-service authentication with least privilege (for example Cognitive Services User) subject to BM&G identity standards.

Create a unique constraint on IdempotencyKey. Before invoice creation, acquire a database/application lock. Persist the invoice number immediately after creation; any later retry must reuse it.
12. Failure Handling and Recovery
Transient retry
Use exponential backoff with jitter for network/VPN timeouts, Document Intelligence 408/429/5xx, and temporary LoanTrack/EDM failures. PoC baseline: four attempts with approximately 2s, 5s, 15s, and 30s delays, respecting server retry hints when available.
Non-retryable examples
unsupported/password-protected file
unknown document class below threshold
missing required invoice metadata
unresolved source conflict
LoanTrack business validation failure
authentication/authorization misconfiguration
CRITICAL RECOVERY RULE
If invoice creation succeeds and EDM upload fails, never create a new invoice. Persist the invoice number first, then retry only the EDM stage against the same invoice. Partial multi-document EDM retries should skip already confirmed uploads.
