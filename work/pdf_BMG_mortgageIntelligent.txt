Business Understanding & Current-State ChallengesBM&G provides mortgage closing document examination and review services to lenders operating in Texas and adjacent states. Under Texas law, an attorney must review loan closing documents - making this a legally mandated, high-volume service. The firm serves approximately 300 lender clients, with the top 45 lenders accounting for around 80% of total business volume. Examination - reviewing documents and delivering a supplemental closing package - constitutes 80–90% of the firm’s total workload.The examination process flows through three stages: Intake, Processing, and Release. Each transition between stages is currently a manual human step with no automation at any boundary.•Intake: Lender uploads documents via JetDocs. Staff manually creates a transaction in LoanTrack, assigns an invoice number, uploads documents to EDM, and places the file in the MS Access queue.•Processing: A Legal Assistant picks up the file from the Access queue. They open ClosingExpress, manually read every document in the closing package, and enter approximately 140 data fields across seven input screens. They then perform a stare-and-compare review against the Review 1 checklist.•Release: The Legal Assistant generates the supplemental closing package via ClosingExpress and delivers it through SecureDocs to the lender or title agent.The following challenges were identified through discovery sessions, system documentation review, and analysis of the examination process spreadsheet:•No integration at any system boundary. Every stage transition is a manual human step, introducing lag and error risk.•Legacy technology stack. LoanTrack runs on end-of-life Silverlight. JetDocs is aging ASP .NET. MS Access is not a production workflow system.•Manual data extraction. Legal Assistants hand-key approximately 140 fields per file from six document types. This is the primary driver of handling time.•Rework rates up to 60% on some accounts. Missing or incomplete documents are not detected at intake - they are discovered by the examiner mid-review, triggering manual email chains.•Zero operational visibility. No real-time SLA dashboard. No queue analytics. Management cannot see the current state of operations without asking someone.•Single developer dependency. All custom systems are maintained by one internal developer. Any change, fix, or integration requires a single person with no documented backup.Current-State ChallengesCurrent Operational Workflow

Core Platform ComponentsDocument Ingestion Pipeline
1Handles PDF text extraction, OCR fallback for scanned documents, multi-document PDF splitting, and AI-based document type classification. Classifies each document as Note, Deed of Trust, Title Commitment (Schedules A/B/C), Survey, Closing Instructions, or Rider before extraction begins.AI Extraction Engine
2LLM-backed extraction service processing approximately 140 defined data fields across all six document types. Per-document-type prompts return structured JSON with confidence scores per field. Handles Note, DOT, Title Commitment, Survey, Closing Instructions, and Rider extraction in a coordinated pass. Lender code lookup auto-populates lender-specific defaults.Business Rules Engine
3Configurable rules covering Note compliance (form type, late charge, grace period), DOT validation (date match, prepared-by, marital status), Title Commitment checks (effective date, title holder, Schedule C lien identification), Home Equity rules (3% fee cap, 80% LTV, owner occupied), and Survey checks. Rules are data, not code - firm staff can update parameters without engineering involvement.Data Verification Report
4Configurable rules covering Note compliance (form type, late charge, grace period), DOT validation (date match, prepared-by, marital status), Title Commitment checks (effective date, title holder, Schedule C lien identification), Home Equity rules (3% fee cap, 80% LTV, owner occupied), and Survey checks. Rules are data, not code - firm staff can update parameters without engineering involvement.Dynamic Queue Orchestration
5Multi-office, multi-POD routing engine. Queue assignment considers office, loan type, client, and POD availability. Prioritization applies in order: closing date today, rush flag, SLA aging, core client status, FIFO. Only approved staff within the assigned POD can see and claim a file. Manager override for reassignment and rush re-prioritization.Legal Assistant QC Workbench
6Split-pane interface: extracted fields on the left grouped by input section, source document on the right. Each field is linked to the page and region it was extracted from. Clicking a field jumps the document view to the relevant highlighted section. Fields are color-coded by status: green (high confidence), amber (low confidence), red (rule violation or mismatch). Legal Assistants work through flagged items, confirm or correct, and every correction is logged as a structured feedback event.Supplemental Package Generation
7ClosingExpress wrapper service calls the generation engine with the completed field set. Template selection is determined by loan type, purpose, and lender code. The generated supplemental package is captured and stored in EDM.Client Portal
8Authenticated lender-facing portal supporting all five submission types. Real-time order status visible from submission through release. Supplemental package available for download immediately on release, with option to forward directly to title or settlement agent.

Security, Compliance & Risk ManagementSecurity ArchitectureThe platform handles sensitive mortgage documents including PII, financial data, and legal instruments. Security is not a Phase 3 consideration - it is designed into the platform from Sprint 0.•On-premises deployment for all platform services.
